## Delivered boundary

Phase 6-D2B adds the provider-neutral durable delivery boundary over the
validated terminal D2A/D1 alert outbox, in one new package
`src/turtle_value_engine/monitoring_delivery/`:

- `contracts.py` — typed immutable `DeliverySettingsV1`,
  `MonitoringDeliveryIntentV1` (persisted **before** any outbound I/O),
  `MonitoringDeliveryAttemptV1` (one immutable record per HTTP exchange,
  response body persisted only as a SHA-256 digest), `MonitoringDeliveryStateV1`
  (atomic latest state fully derived from immutable artifacts) and the
  canonical bounded `MonitoringWebhookPayloadV1` request body. The
  deterministic `delivery_id` binds runner, activation, alert batch,
  destination id and payload contract version; a changed logical destination
  produces a new delivery identity and cannot inherit a prior `DELIVERED`
  state.
- `store.py` — the separate `DeliveryLedgerStore` (intents/attempts immutable
  create-only via temp+fsync+hardlink, state pointer atomically replaced last,
  canonical-JSON + hash validation on read, symlink/foreign-slot/corruption
  fail-closed, injectable write-failure hook), never mixed into the D1 or D2A
  stores.
- `transport.py` — the generic HTTP webhook transport over `http.client`:
  canonical bounded JSON body, `Content-Type: application/json`, deterministic
  `Idempotency-Key` plus `X-TVE-Delivery-Id`, safe user agent, optional bearer
  authorization, redirects never followed, bounded timeout, bounded response
  bytes, endpoint/userinfo validation that rejects plain http on the live path
  (loopback plain-http exists only through the explicit test-only
  `allow_loopback_http` injection). Endpoint URLs and tokens are never echoed
  into exceptions or persisted state; every failure is a stable machine code.
  Status semantics are explicit: 2xx → `DELIVERED`; 429/5xx →
  `RETRYABLE_FAILURE`; other 4xx and 3xx → `PERMANENT_FAILURE`; connect
  failures proven pre-dispatch → retryable; post-dispatch timeout/connection
  loss → `AMBIGUOUS`. No exactly-once claim is made for arbitrary receivers.
- `service.py` — `MonitoringDeliveryService`: re-validates the exact terminal
  `RunnerReceiptV1` plus `MonitoringCycleResultV1`/`MonitoringAlertBatchV1`
  pair (identity and hash binding) before any transport call, persists the
  immutable intent first, performs bounded clock-injectable attempts with
  persisted bounded exponential backoff, derives the latest state purely from
  immutable artifacts (byte-identical crash repair), treats `AMBIGUOUS` as
  terminal with automatic resend forbidden unless the configuration explicitly
  declares receiver-enforced idempotency on the delivery key, turns retry
  exhaustion into terminal `PERMANENT_FAILURE`/`RETRIES_EXHAUSTED`, and
  produces `NOOP` with zero network I/O for an empty outbox. Delivery never
  invokes the D1 boundary, a provider, a model or re-analysis.

Configuration extends the typed `ProjectConfig` under the nested
`[monitoring.delivery]` object (disabled by default in the checked-in
example): non-secret policy plus `SecretReference` endpoint/auth references
resolved only in process memory at call time. The safe summary shows
destination id and reference names only.

The CLI surface is `tve watch deliver --runner-config <path>
--project-config <path> [--activation-id <id>] --network deny|allow` (exit 0
`DELIVERED`/`NOOP`, 4 recorded failure states, 2 fail-closed) and
`tve watch delivery-status --delivery-root <path> [--delivery-id]
[--activation-id]` (bounded, secret-free). Five checked-in JSON schemas with
drift tests cover the settings, intent, attempt, state and payload contracts.

No D2A/R1 lease/activation/receipt rule, D1 cycle identity, Phase 6-A cursor
semantics, Phase 6-B acquisition, Phase 6-C execution, `strict-v1`, valuation,
hard gate or adjustment-approval semantics changed.

## Automatic verification

`tests/test_monitoring_delivery.py` adds 43 deterministic cases driving the
public service/CLI boundaries over genuine terminal D1/D2A artifacts produced
by injected fakes, a real loopback HTTP receiver or an injected transport with
a fake clock. Proven automatically:

- schema drift for all five new persisted/payload contracts;
- deterministic delivery identity binding (destination/contract changes
  produce new identities);
- alert-batch tamper, missing D1 terminal pair, foreign/missing runner
  receipt → fail before any transport call with zero D1 reruns;
- network deny with `socket.socket` monkeypatched → typed error, zero socket
  I/O, zero ledger writes; CLI deny path exits 2 with nothing persisted;
- disabled delivery and unresolved endpoint reference fail closed;
- empty outbox → terminal `NOOP` with zero requests, also on rerun;
- loopback 2xx success with byte-exact canonical body, `Idempotency-Key` /
  `X-TVE-Delivery-Id` headers, `Content-Type: application/json`, bearer
  authorization, user agent, response digest-only persistence, terminal
  `DELIVERED` state binding the terminal attempt hash;
- rerun after `DELIVERED` performs zero HTTP requests (service and CLI);
- 503 then 429 then 200 → bounded in-invocation retry with monotonic attempt
  numbers 1..3; persisted backoff scheduling proven with a fake clock (not-due
  wake performs zero requests; due wake performs exactly one);
- bounded exponential backoff cap; retry-budget exhaustion → terminal
  `PERMANENT_FAILURE`/`RETRIES_EXHAUSTED` with no further requests;
- permanent 404 → exactly one attempt, no retry storm on rerun;
- injected post-dispatch timeout and real loopback abrupt disconnect →
  terminal `AMBIGUOUS`, never resent by default; resent only when
  receiver-enforced idempotency is explicitly declared;
- oversize loopback response → bounded read, digest suppressed,
  `RESPONSE_BYTES_EXCEEDED` recorded; 301 → `PERMANENT_FAILURE` redirect not
  followed with a single request; refused connect → pre-dispatch retryable;
- live transport requires https and rejects userinfo/invalid schemes before
  any socket;
- crash after intent before request → same delivery resumed (attempt 1),
  zero D1/provider work; crash after response before state publication →
  deterministic repair with zero new requests and byte-identical state;
  state-pointer loss → byte-identical repair;
- repeated delivery failures across four wakes never rerun D1 or the
  acquisition provider;
- corrupt, non-canonical and foreign-slot ledger artifacts and impossible
  published states fail closed;
- secret canaries (webhook URL path token and bearer token) are absent from
  every ledger file, status projection, CLI JSON output, endpoint-error
  exception text and the config safe summary; the safe summary shows
  reference names only;
- CLI exit codes (0 success, 4 recorded failure, 2 fail-closed) and the
  bounded secret-free `delivery-status` projection;
- static import check: no delivery module imports provider/research/pipeline/
  preparation code, and the lower monitoring packages do not import delivery.
