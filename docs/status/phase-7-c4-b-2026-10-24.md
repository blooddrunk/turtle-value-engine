## 1. What was built

* `src/turtle_value_engine/evolution/activation_status.py` — the new
  strictly-read-only inspection boundary. `inspect_activation_status()` reuses
  the executor's own fail-closed guards (`_guard_activation_root`,
  `_guard_target_config`, `_guard_activation_store`) read-only, then performs
  one scan pass over `journal/`, `receipts/`, `before-images/`, `rollbacks/`
  (plus root-level entry validation; `locks/` is containment-checked but never
  scanned — leftover lock entries are operational state, not history) and
  classifies the observed bytes into the versioned
  `ProfileActivationStatusV1` (`profile_activation_status_v1`, checked-in
  drift-parity schema `schemas/profile-activation-status.schema.json`).
* `tve evolution activation-status --activation-root ... --project-config ...`
  (optional `--receipt <path>` for additive exact-record facts). There is
  deliberately **no `--output`**: printing a report file would itself be a
  persistent write. Exit classes: `0` verified informational
  (`NO_HISTORY` / `ACTIVATED_VERIFIED` / `ROLLED_BACK_VERIFIED`), `1` every
  pending/diverged/ambiguous/corrupt outcome (full projection still printed),
  `2` unusable input (the executor's classified guards; e.g.
  `ACTIVATION_ROOT_SYMLINK`, `ACTIVATION_STORE_SYMLINK`, `CONFIG_PATH_*`,
  `RECEIPT_INVALID` for a supplied receipt file).
* `docs/operations/profile-activation-executor.md` §4 — the Chinese
  "当前状态 / 下一步" quick start with the literal command, the nine-status
  table (status, exit code, meaning, next action), the `problems` /
  `observations` / `guidance_zh` / `focal` field explanations and the explicit
  limits (historical receipts do not prove present owner consent;
  `owner_authority_revalidated=false`; no global atomic snapshot).

### Classification rules (goal §2 items 1–8)

Structural problems (corrupt/foreign/symlinked/nonregular/out-of-root
artifacts, `RECEIPT_WITHOUT_JOURNAL`, `RECEIPT_JOURNAL_MISMATCH`,
`ROLLBACK_UNASSOCIATED`, `ROLLBACK_CONTENT_MISMATCH`, root foreign entries)
are collected first and force `CORRUPT_OR_UNVERIFIABLE` — no verified-green
state can coexist with a named problem. Otherwise the byte-truth decision
tree is:

1. `>1` unfinished (receipt-missing) relevant intents → `AMBIGUOUS_HISTORY`
   (mirrors the executor's `ACTIVATION_INTENT_AMBIGUOUS`).
2. exactly one unfinished intent: config = activated hash →
   `RECEIPT_FINALIZATION_PENDING`; config = prior hash → `APPLY_RESUMABLE`;
   neither → `CONFIG_DIVERGED` (`UNFINISHED_INTENT_CONFIG_DIVERGED`).
3. no unfinished intents: config = some finished activation's activated hash →
   `ACTIVATED_VERIFIED` (a simultaneously present rollback outcome is the
   honest `STALE_ROLLBACK_OUTCOME_PRESENT` observation; a present rollback
   intent without outcome is `ROLLBACK_INTENT_PENDING_RESTORE`); config =
   prior hash with bound intent but no outcome →
   `ROLLBACK_FINALIZATION_PENDING`; config = prior hash with valid outcome →
   `ROLLED_BACK_VERIFIED`; config = prior hash with neither →
   `CONFIG_DIVERGED` + `RESTORED_WITHOUT_DURABLE_PROOF` (an owner-reverted
   config is never fabricated into a verified rollback); anything else →
   `CONFIG_DIVERGED` + `POST_ACTIVATION_CONFIG_DIVERGED`.
4. no relevant histories at all → `NO_HISTORY` (missing store stays missing).

Before-image verification honours the executor's write order
(journal → before-image → replace → receipt): finished activations and
config-provably-replaced intents must carry a valid image; an unfinished
intent whose config still holds prior bytes may legitimately have crashed
before the image was persisted. Unrelated histories (other configs) are
counted and observed (`UNRELATED_HISTORIES_PRESENT`) but never labelled
current. `locks/` is never scanned.

## 4. Explicit limits and non-claims

* The status projection is a **single-pass observation**:
  `global_atomic_snapshot_claimed=false`. A concurrent apply/rollback may
  change bytes between reads; no bounded re-read loop is claimed.
* **Owner authority is never re-validated**: `owner_authority_revalidated`
  is a fixed `false`. A historical receipt is audit evidence, not present
  owner consent. Fresh authorization questions belong to a fresh preview.
* `locks/` contents are deliberately not classified (operational state).
* Exit-2 input guards are the executor's own; corruption *inside* a
  well-formed store is reported, never auto-repaired.
* CI evidence for this implementation is the exact PR-head Actions run on
  this branch (linked in the PR); merge-head and latest-main re-checks follow
  the repository's standard post-merge practice.
