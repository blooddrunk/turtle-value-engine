### Key behavioral proofs (from the 34 focused tests)

- **Happy path end-to-end**: a real (throwaway) Ed25519 signature over the
  canonical decision input, verified against the registered key, flows
  through `validate_owner_decision(verifier=SignedOwnerProvenanceVerifier(
  ...))` → `VALID` + `OWNER_AUTHORITY_VERIFIED` record →
  `plan_profile_activation(...)` → `REVERIFIED` /
  `READY_FOR_EXPLICIT_OWNER_EXECUTION` with `execution_performed=false` and
  `automatic_activation_allowed=false`.
- **Only a positive allowlist result passes** (C2-R2 rule preserved):
  `allowlist_matched=True` is returned solely on a registry identity
  binding; every other identity state REJECTS.
- **Replay-proof**: cross-decision (ACCEPT↔REJECT, different content),
  cross-context (different bindings) and cross-purpose (signature over a
  foreign domain) reuse all fail `SIGNATURE_VERIFIED`/`DECISION_CONTENT_
  BINDING`; only the canonical byte form may be signed (anti-malleability).
- **Substitution-proof**: an ACCEPT record whose provenance points at
  signed REJECT bytes is rejected with
  `OWNER_PROVENANCE_RECORD_INPUT_BINDING_MISMATCH` and the plan stays
  BLOCKED; a record about other bytes fails the provenance-hash binding.
- **Fail-closed keys**: unknown, revoked, out-of-window (including
  malformed decision dates), scope-exceeding and foreign-identity keys each
  fail their canonical check; a missing `cryptography` installation fails
  closed with the classified `[provenance]`-extra error.
- **No backdoor**: source scans prove the CLI has no verifier wiring or
  selector (`SignedOwnerProvenanceVerifier`, `owner_provenance`,
  `--verifier`, `--registry` absent from `cli.py`) and the module has no
  `os.environ`/`getenv`/trust override; production code never signs and
  never holds private key material.
- **Offline and deterministic**: socket-guarded verification (pure function,
  verifier assessment and plan integration construct no socket); identical
  inputs replay byte-identical dossiers; no wall-clock fields anywhere.
- **Schema**: three drift-parity schemas; the verification schema pins the
  exact nine-check sequence; reordering, duplication, truncation and
  VERIFIED-with-failures dossiers are rejected by the model.

## 5. Remaining limitations

- The CLI constructs no verifier (by design). Wiring provenance into
  `record-decision`/`plan-activation` with an explicit `--key-registry`
  input is C3-B scope; until then a hosting process injects the verifier
  through the library boundary only.
- Registry lifecycle (initial registration, rotation, revocation workflow)
  is manual JSON today; C3-B owns trusted identity registration, evidence
  capture and revocation tooling.
- Verification-side timing side channels are out of scope (no secret is
  processed during verification); private-key compromise mitigation is key
  custody + explicit registry revocation, both documented in the
  architecture doc's threat model.
- The statement's validity window compares owner-declared key dates against
  the signed decision's `decided_at` (deterministic); a key compromised
  *after* a genuine signing still verifies that historical signature unless
  the key is revoked in the registry — revocation is the explicit control.

## 6. Manual owner actions deferred to C3-B (recorded, none required for
C3-A closure)

Generate an offline Ed25519 keypair; register the public key (identity,
scope, validity window) in a trusted registry file under owner control
outside Git; sign the canonical decision-input message with the private key
(per `docs/architecture/owner-provenance-verification.md` §6); keep the
private key outside chat/Git and revoke in the registry on compromise.
C3-B must provide capture tooling and an explicit CLI boundary for these
steps; none of them may be automated on the owner's behalf.

## 7. Next-phase recommendation

**Phase 7-C3-B — trusted identity registration, evidence capture and
