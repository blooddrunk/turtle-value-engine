## 1. Gap determination: implementation, not a redundant runbook

The goal required inspecting existing output first and preferring a tested
documentation-only outcome if an existing command suffices. On baseline
`daf2506` the six required determinations need **four separate commands with
disjoint inputs**, and the most common operator state has **no machine view at
all**:

| Required determination | Existing source | Gap |
| --- | --- | --- |
| 1–2. Pair/manifest identity + verified bytes | `audit-profile` | nothing about decision, store, or next steps |
| 3. CDC 14% vs 12% question + 13% contrast | `decision-dossier` | **requires `--output` — cannot run zero-write** |
| 4. Decision exists; authority revalidated | `plan-activation` / `activate-profile` preview | **both require `--decision-record` at argparse level** — without a decision (journey start) they exit 2 with a usage error and no classified payload |
| 5. Blocked / preview-ready / applied / rolled back / interrupted / unverifiable | preview **and** `activation-status` | no single output combines plan state with store classification |
| 6. Next safe operation | scattered (`guidance_zh`, runbooks) | no combined cross-journey next-step view |

Concrete baseline probes (all on the pristine `daf2506` checkout):

1. `tve evolution activate-profile ... --project-config ... --activation-root ...`
   (no `--decision-record`) → exit 2, argparse: `error: the following
   arguments are required: --decision-record`.
2. `tve evolution plan-activation ...` (same) → exit 2, same refusal.
3. `tve evolution decision-dossier ...` (no `--output`) → exit 2: `error: the
   following arguments are required: --output` — the policy-question material
   is unavailable from any zero-write command.
4. The new user-journey suite run in a pristine baseline worktree at
   `daf2506` fails collection: `ModuleNotFoundError: No module named
   'turtle_value_engine.evolution.owner_readiness'`.

A runbook cannot fix 3/4 above (the machine views do not exist for those
states), so the goal's own criterion — "write a failing user-journey test
demonstrating what the existing separate outputs cannot convey as a single
actionable read-only summary" — selects the additive implementation.

## 2. What was added

- `src/turtle_value_engine/evolution/owner_readiness.py`: the immutable
  `OwnerReadinessSummaryV1` (`owner_readiness_summary_v1`, frozen,
  extra-forbid, `content_sha256`-self-verifying) and
  `summarize_owner_readiness()`. It **reuses** the established verification
  paths — a fresh `audit_profile_semantics` (C1), a fresh
  `plan_profile_activation` (C2-R1; its `authority_reverification_status`
  `REVERIFIED` is the *only* source for `owner_authority_revalidated=true`)
  and, when supplied, the unchanged `inspect_activation_status` (C4-B) — plus
  a derived `journey_state` (11 documented values, precedence:
  store-pending/attention → applied/rolled-back → published-pair-blocked →
  decision states → preview-ready → other blocked) and deterministic Chinese
  `policy_question_zh` / `behavior_contrast_zh` / `next_steps_zh` composed
  only from derived facts (thresholds from the parsed target profile; the
  contrast row is the first decision-changed row of the real engine boundary
  replay — exactly 13.0% for the published pair; next-step commands are
  shell-quoted read-only commands). Fixed literals:
  `requires_human_policy_approval=true`,
  `automatic_activation_allowed=false`, `execution_performed=false`,
  `summary_is_informational_not_authorization=true`, `read_only_observation=true`.
- CLI: `tve evolution readiness-summary` (additive; required
  `--base-profile/--target-profile/--release-manifest/--project-config`;
  optional `--activation-root` and the existing optional decision/exception/
  revocation/trust-root/authority-evidence/lifecycle inputs). The handler
  reuses `_prepare_activation_inputs` (the same verifier/trust-root wiring as
  plan/activate), guards the config/store with the unchanged read-only
  `_guard_target_config` / `_guard_activation_root`, and writes nothing.
  Exit 0 for every informational outcome (a blocked readiness is a fact, not
  a command failure — there is no `--output` and no exit-1 success path);
  exit 2 for classified unusable input. No new parser/validator was written.
- `schemas/owner-readiness-summary.schema.json`: checked-in Draft 2020-12
  schema with drift-parity test (exactly the pattern of
  `profile-activation-status.schema.json`).
- `docs/operations/owner-readiness-handoff.md`: the Chinese operator
  instructions (single journey, field/state lookup tables, boundary
  statements, linkage to the existing executor/provenance runbooks).
- `tests/test_owner_readiness_summary.py`: 30 focused tests (below).

   command answers all six determinations; `OWNER_DECISION_REQUIRED`
   informational; 14%/12% question with raw decimals; 13.0% contrast; store
   `NO_HISTORY`; byte-identical repeat; missing store stays missing; zero
   writes (whole-tree snapshot before/after).
2. Authenticated ACCEPT (real registry init → sign → record → capture):
   `PREVIEW_READY`, `owner_authority_revalidated=true` from the real fresh
   re-attestation, no `--apply` in next steps; the real executor preview
   still derives READY afterwards; no store created when root omitted.
3. REJECT: terminal `REJECTED_BY_OWNER`, no authority claim
   (`owner_authority_revalidated=false` — the plan re-attests only
   ACCEPT_VERIFIED resolutions).
4. Revoked key (real `registry revoke` then summary): `OWNER_AUTHORITY_NOT_PROVEN`
   with the nested `OWNER_AUTHORITY_REVERIFICATION_*` blocker; ACCEPT without
   trust root: `OWNER_AUTHORITY_REVERIFICATION_REQUIRED`; conflicting
   ACCEPT+REJECT (both validly signed by the registered key): `DECISION_CONFLICT`.
5. Store states through the **real executor**: applied → `ALREADY_APPLIED`;
   rolled back → `ROLLED_BACK`; injected `journal_persisted` fault →
   `RECOVERY_PENDING`; tampered receipt → `STORE_NEEDS_ATTENTION` with named
   problems; config already target without history → `ACTIVATION_BLOCKED`
   (`DEFAULT_ALREADY_TARGET`); tampered target profile → `PUBLISHED_PAIR_BLOCKED`,
   `published_bytes_verified=false`.
6. Input guards: missing/symlinked profile, malformed decision record, missing
   config, evidence-without-trust-root → classified exit 2, no traceback, zero
   writes.
7. Boundary invariants: socket-guarded execution (no network construction),
   no PEM/private-key material in output, fixed literals, documented
   `JOURNEY_STATE_VALUES` enumeration, schema drift parity, no authorization
   field names, `summary_id` deterministic and bound to observed facts.
8. Compatibility controls: genuine apply → summary (`ALREADY_APPLIED`) →
   idempotent re-apply (`COMPLETED_ALREADY`) → rollback (`ROLLED_BACK`) all
   still pass through the unchanged executor; literal `python -m` subprocess
   journey smoke.

## 5. Boundary statements and limitations

- The summary is **not** an authorization bearer, immutable snapshot or
  permission to apply; a READY plan observed by it expires conceptually with
  its inputs/trust root, and the apply boundary re-derives under its own lock
  and expected hashes (unchanged C4-A semantics).
- Store facts are the unchanged single-pass, non-global-atomic C4-B
  projection; `activation-status` remains the store authority.
- `journey_state` is a derived informational view over unchanged plan/audit/
  store facts; all source codes keep their established names and exit
  classes (nested, never recoded).
- After a rollback with a still-valid decision the plan may be READY while
  the journey reports `ROLLED_BACK` — honest bytes-first reporting; a
  provable new activation needs a different decision record (unchanged C4-B
  semantics, documented in the operations manual).
- No live owner key, network account, market data, or manual fixture
  assembly was used; no `--apply`, rollback, approval, signature or owner
  identity was invoked or synthesized anywhere in this phase.
- CI-equivalent Dashboard steps were executed on this WSL2 host (node 24 /
  pnpm 11.23.0) with the CI sentinel environment; GitHub Actions itself runs
  the unchanged workflow at the PR head (see §6).
