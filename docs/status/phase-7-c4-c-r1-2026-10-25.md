## 3. The minimal repair

1. **Safe composition (F1):** every executable next-step command is now
   composed from its exact argument vector via `shlex.join` and appears
   only as the final segment after the last full-width colon of a step.
   Bare `<placeholder>` fragments no longer exist anywhere in
   `next_steps_zh`. Operator paths with spaces, quotes, semicolons, `$`,
   backticks and redirection characters are quoted and round-trip
   byte-for-byte.
2. **Replay fidelity (F2):** the CLI handler passes the bounded, frozen
   `ReadinessReplayInputsV1` (paths only — never secret material —
   per-option order and multiplicity preserved, capped list sizes); the
   displayed readiness-summary retry quotes every explicitly supplied
   input (`--boundary-input`, `--decision-record`, `--revocation`,
   `--policy-exception`, `--trust-root`, `--authority-evidence`,
   `--signed-revocation`, `--signed-supersession`, `--activation-root`).
   Re-running the displayed command reproduces the identical
   `summary_id`/journey/authority observation (asserted through the real
   CLI, including the verified `PREVIEW_READY` case and the
   revoked-key `OWNER_AUTHORITY_NOT_PROVEN` case). Without CLI provenance
   (pure library callers) no retry command is displayed at all — prose
   explains what must be preserved.
3. **Honest write labeling (F3):** `decision-dossier` and
   `plan-activation` (both require an operator-chosen `--output` and write
   a file) are described in prose that names the required inputs, requires
   the operator to choose the output path, and explicitly discloses the
   write; they are never emitted as paste-ready executable text. The
   `PREVIEW_READY`/`ROLLED_BACK` preview guidance no longer fabricates a
   preview command when `--activation-root` (parser-required) or the
   decision inputs are unknown — prose names exactly what is missing.
   Every emitted executable command is a complete read-only operation
   (`readiness-summary` / `activation-status` / `activate-profile` preview
   without `--apply`).

The persisted summary contract is unchanged: no model field, schema,
journey state, exit class or literal changed (`schemas/
owner-readiness-summary.schema.json` is byte-identical; its drift-parity
test stays green). The new `ReadinessReplayInputsV1` is an ephemeral
hint-provenance parameter, not a persisted contract.

## 5. summary_id diagnostic (goal §3, not fixed in R1)

`test_diagnostic_summary_id_shared_across_distinct_store_problems` held
the whole decision context and store identity fixed and added one foreign
entry to the same store between two summaries: same
`activation_store_status` (`CORRUPT_OR_UNVERIFIABLE`), **different**
`activation_store_problems`, **different** `content_sha256`, **same**
`summary_id`. The review's hypothesis is therefore reproduced as a real
(if narrow) identity weakness: `summary_id` binds the store status but not
the store problems/guidance. Per the goal this is logged, pinned by the
diagnostic test, and **deliberately not repaired here**; any fix is a
separately scoped, version-aware identity-contract task.
