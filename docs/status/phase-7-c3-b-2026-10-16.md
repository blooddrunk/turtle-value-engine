## 2. What was implemented

### Work package A — trusted registry and evidence operations

1. **Versioned trust-root store**
   (`evolution/owner_trust_store.py`): `OwnerProvenanceRegistrySnapshotV1`
   wraps one full `OwnerProvenanceKeyRegistryV1` with a sequence number, a
   content-hash link to its parent (sequence 1 has none) and its own
   deterministic id + full-content SHA-256. The same key set under
   different trust content is a distinct snapshot identity (R2's
   content-snapshot rule applied to the store). Loading validates the
   whole chain fail-closed (contiguity from 1, parent links, model-level
   tamper detection, foreign files); publication is one exclusive
   `O_CREAT|O_EXCL` open (byte-identical appends idempotent; foreign
   content a classified immutable error; symlinks refused; inode-guarded
   failure cleanup). Trust lifecycle — `enroll`, `revoke` (mandatory
   reference), `rotate` (old revoked + new enrolled in ONE atomic
   snapshot, single sequence increment) — is pure snapshot transitions;
   committed snapshots are never rewritten.
2. **Immutable evidence bundles**: one create-only directory per
   deterministic `bundle_id` holding the exact canonical decision-input
   bytes, the signed statement, the registry snapshot trusted at capture
   time, the verification dossier and the resulting record (or `null`),
   bound by `OwnerProvenanceEvidenceBundleV1`
   (`capture_is_evidence_not_authority` fixed). Capture runs the real
   record-time boundary plus the pure dossier; a non-verifying signature
   yields an honest INVALID/REJECTED bundle.
3. **Offline re-verification**: the strict loader
   (`load_owner_decision_evidence`) fail-closes consumers on any
   component/binding hash mismatch; the audit re-verification
   (`reverify_owner_decision_evidence`, `EvidenceReverificationV1`)
   *compares* — recomputing the dossier from the actual persisted bytes —
   so tampering and even a fully self-consistent forged dossier surface as
   a named `MISMATCH`; byte-identical inputs replay byte-identically
   (socket-guarded).
4. **CLI (the real verifier only)**: `tve provenance registry
   init|enroll|revoke|rotate|status`, `tve provenance verify-evidence`
   (exit 0 replays / 1 mismatch), `tve evolution record-decision
   --signed-statement --trust-root [--evidence-root]` (VERIFIED capture;
   the unsigned flow stays byte-compatible), `tve evolution
   plan-activation --trust-root --authority-evidence
   [--signed-revocation…] [--signed-supersession…]` re-attesting authority
   freshly against the trust root's **latest** snapshot — registry
   revocation takes effect immediately (proven end-to-end: revoking the
   key flips a READY plan to BLOCKED `OWNER_AUTHORITY_REVERIFICATION_REJECTED`).
5. **Trust-root ownership**: the trust root is an operator-supplied path;
   no decision artifact field designates it (none exists — pinned by
   test); the CLI refuses a trust root located inside a submitted decision
   bundle directory and decision artifacts stored inside the trust root;
   there is no verifier selector, no environment-derived trust and no
   fake-verifier path (the CLI constructs `SignedOwnerProvenanceVerifier`
   at exactly two authorized sites, source-scanned).

### Work package B — authenticated revocation and supersession

1. **Protocols** (`evolution/owner_lifecycle.py`):
   `turtle-value-engine:owner-decision-revocation:v1` over
   `OwnerRevocationPayloadV1` (exact revoked record id AND content
   SHA-256, target binding, identity, date, rationale, source revision)
   and `turtle-value-engine:owner-decision-supersession:v1` over
   `OwnerSupersessionPayloadV1` (both records bound by id and content
   SHA-256, shared target), each with a detached Ed25519 statement and a
   deterministic verification dossier pinned to its canonical eight-check
   sequence (ALGORITHM_SUPPORTED, KEY_RESOLUTION, KEY_IDENTITY_BINDING,
   KEY_VALIDITY_WINDOW, KEY_NOT_REVOKED, PAYLOAD_CONTENT_BINDING,
   PURPOSE_BINDING, SIGNATURE_VERIFIED). Verification is pure/offline
   against the same trust root; a key may sign lifecycle statements when
   enrolled, identity-bound, in-window and not revoked.
2. **Resolver** (`owner_decision.py`, additive):
   `AuthenticatedRevocationBindingV1` /
   `AuthenticatedSupersessionBindingV1` are plain content-bound carriers
   produced only by fresh verification; each must match an actually
   supplied record byte-exactly (id, content hash, target) or the
   resolution fails closed; cycles and double supersession fail closed
   across unsigned + authenticated links; exact duplicate bindings
   collapse idempotently; unsigned revocation/supersession semantics and
   the C3-A-R1 plan blockers are unchanged; the resolution carries
   `authenticated_revoked_record_ids` / `authenticated_superseded_record_ids`
   in its identity derivation.
3. **Plan** (`activation_plan.py`, additive): signed statements are
   verified **freshly inside the plan** against `lifecycle_trust_root` —
   without one, any statement blocks (`LIFECYCLE_TRUST_ROOT_REQUIRED`);
   a failing statement blocks (`SIGNED_REVOCATION_REJECTED:*` /
   `SIGNED_SUPERSESSION_REJECTED:*`). Only a fully verified statement may
   remove a record. An authenticated revocation of a dissenting REJECT
   legitimately resolves a conflicting set (the owner's own signed
   statement, verified fresh); unsigned metadata still can never increase
   authorization (pinned). The plan carries the authenticated ids in
   `plan_id`.
