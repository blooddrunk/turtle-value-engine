## 1. What was implemented

- `src/turtle_value_engine/evolution/owner_decision.py`:
  - `OwnerPolicyDecisionInputV1` (`owner_policy_decision_input_v1`): the
    human-authored unsigned submission (decision
    `ACCEPT_WITH_EXCEPTION|REJECT`, complete declared bindings, rationale,
    declared owner identity, decided_at, source revision). A C1
    `PolicyApprovalClaimV1` is a different contract and never maps onto it.
  - `OwnerPolicyDecisionRecordV1` (`owner_policy_decision_record_v1`):
    immutable, canonical id + content hash over every bound field including
    the rationale; binds base/target profile byte hashes, release manifest
    id+content hash, fresh audit id+content hash, and the exception by
    **both** deterministic id **and** full content hash; fixed literals
    `requires_authenticated_owner_authority=true`,
    `automatic_application_allowed=false`,
    `decision_is_not_execution_request=true`.
  - `DecisionProvenanceV1` + `OwnerAuthorityAssessmentV1`: provenance binds
    the exact submitted bytes (LOCAL_UNSIGNED_JSON + content hash +
    source revision); authority separates `OWNER_AUTHORITY_UNVERIFIED /
    OWNER_AUTHORITY_VERIFIED / OWNER_AUTHORITY_REJECTED` from artifact
    validity, with the explicit trust statement that an unsigned local
    JSON, an EnvironmentFile username, Git author text, CI success and
    publication prove neither authorship nor permission, and an allowlist
    is not authentication.
  - `OwnerDecisionVerifier` ABC: the injected-verifier trust-model
    interface. No implementation ships with the CLI; there is no
    CLI-selectable verifier (fake verifiers are test fixtures injected
    through the library only).
  - `validate_owner_decision()`: re-runs the C1 audit **fresh** from the
    supplied bytes + exceptions (a previous dossier's self-reported
    readiness is never trusted or read) and emits
    `OwnerPolicyDecisionValidationV1`
    (`owner_policy_decision_validation_v1`) with the canonical six-check
    sequence (shape / declared-bindings-vs-bytes / fresh-audit identity /
    exception id+content exactness / full finding coverage / provenance),
    per-position `prefixItems` schema pinning, `VALID` (record embedded)
    or `INVALID` (blockers, no record).
  - `OwnerPolicyDecisionRevocationV1`
    (`owner_policy_decision_revocation_v1`) and
    `resolve_owner_decision_authority()` →
    `DecisionAuthorityResolutionV1`
    (`owner_decision_authority_resolution_v1`): fail-closed record-set
    resolution with duplicate collapse, `CONFLICTING` /
    `AMBIGUOUS` terminal states (never newest-file-wins), revocation and
    same-target supersession (unknown references, self/cycles and double
    supersession fail closed), and stale records reported rather than
    silently discarded.
  - `record_owner_decision_file()`: O_EXCL create-only persistence;
    byte-identical reruns are idempotent no-ops; a different record at the
    same path is refused.
- `src/turtle_value_engine/evolution/activation_plan.py`:
  - `ConfigReferenceV1` + `inventory_activation_config_references()`:
    read-only inventory of explicitly supplied affected configurations
    (project `[profiles] default`, watchlists, normalized inputs, backtest
    dataset manifests, Dashboard surface projections, monitoring runner
    configs). Prior-profile-pinned historical artifacts are
    `BASE_PINNED_PRESERVED` — labelled and never rewritten; foreign /
    missing / unreadable references carry specific blockers.
  - `RollbackPlanV1` + `ProfileActivationPlanV1`
    (`profile_activation_plan_v1`): deterministic plan binding the fresh
    audit, the resolved authority state and the config inventory, with the
    fixed rollback exclusions (no automatic monitoring/notification replay,
    no historical-artifact rewrite) and the fixed literals
    `automatic_activation_allowed=false`, `execution_performed=false`,
    `verified_decision_is_not_execution_request=true`.
  - `plan_profile_activation()`: READY only for `ACCEPT_VERIFIED` + a
    machine-clean fresh audit + a coherent config inventory; everything
    else is `BLOCKED` with specific codes.
  - `build_owner_decision_dossier_markdown()`: deterministic Chinese
    owner decision dossier from a fresh audit (exact hashes, 14%/12%
    threshold relationship, 13% behavioural contrast, the observed
    divergence interval `[8%,14%)`, accept/reject effects, submission
    fields, verification expectations and failure handling), explicitly
    stating it is synthetic boundary evidence, not a performance proof.
- CLI (`tve evolution …`): `record-decision` (exit 0 recorded / 1 invalid /
  2 unusable input or guarded path), `plan-activation` (0 ready / 1 blocked
  / 2), `decision-dossier` (0 / 2). All three refuse symlink outputs,
  outputs over supplied inputs and outputs under published artifact
  directories; outputs are create-only with byte-identical idempotence;
  none constructs a provider, model, transport or socket.
- Schemas (drift-parity tested): `owner-policy-decision-input`,
  `owner-policy-decision-record`, `owner-policy-decision-revocation`,
  `owner-policy-decision-validation`,
  `owner-decision-authority-resolution`, `profile-activation-plan`.

## 6. The only human step, when real acceptance is requested later

Automation first generates the Chinese dossier:

```bash
python -m turtle_value_engine evolution decision-dossier \
  --base-profile rules/strict-v1.yaml \
  --target-profile rules/strict-v2.yaml \
  --release-manifest docs/releases/strict-v2/release-candidate.json \
  --output /tmp/strict-v2-owner-decision-dossier.md
```

The owner then chooses `ACCEPT_WITH_EXCEPTION` (retain 14% despite the
12% S/tier thresholds) or `REJECT` (retain strict-v1; a corrected policy
needs a new release), authors the decision-input JSON (exact fields in
`docs/architecture/owner-policy-decision-and-activation-plan.md`), and
records it through `tve evolution record-decision`. Without a real
authenticated source the record stays visibly unverified and every plan
reports `OWNER_AUTHORITY_UNVERIFIED` with the exact blocker — activation
is never claimed.
