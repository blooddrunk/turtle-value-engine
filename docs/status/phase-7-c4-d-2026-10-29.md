## 1. The decision (Option A)

**v1 `summary_id` remains the semantic observed-core identity;
`content_sha256` remains the exact full-projection identity.** The R1
diagnostic collision (two different store problem sets under one status
sharing one `summary_id`, distinguished by `content_sha256`) is a
**documented deliberate property of v1**, not a defect. No consumer bug was
reproduced (there is no repository consumer that deduplicates, caches,
persists or authorizes on `summary_id`), so Option B has no target, and no
real requirement invalidates v1 (Option C is unjustified today).

### Decision table

| Option | Content | Evidence trigger | Assessment |
| --- | --- | --- | --- |
| **A (selected)** | Keep v1 semantic-core `summary_id` + exact-content `content_sha256`; deliver normative documentation (manual + schema/model descriptions) and characterization tests only. | Default; preferred unless a real consumer bug or real external requirement is demonstrated. | No deduplicating/persisting consumer exists in the repository; the collision is presentation-only (problems/guidance/hint text) and always discriminated by `content_sha256`; replay-comparison use cases benefit from the stable semantic id (R3 hint-text changes moved only the content hash, never the id). Zero compatibility risk; no hash cycle introduced; no schema/CLI rollout needed. |
| B (not selected) | Repair a specifically reproduced consumer that incorrectly deduplicates by `summary_id` alone (consumer-side exact key or `(summary_id, content_sha256)` pair). | A failing consumer-level regression on pristine baseline. | No such consumer exists to reproduce: the only production consumer is the CLI's stdout JSON (human-readable, no persistence — the command has no `--output` and nothing in the repository stores a summary). |
| C (not selected; design would be a separate future goal) | Additive, opt-in, separately versioned v2 identity contract whose id binds the complete projection. | A real persisted/external consumer requirement that invalidates both A and B. | No demonstrated requirement. Trade-off known and recorded: a full-projection id would change whenever hint text changes (R3 proved hint edits are routine), destroying the stable semantic-grouping property current replay comparison relies on. If ever needed: v2 must derive its id without self-reference (id excluded from hashed canonical bytes or derived last), keep v1 output coexistence, and pin schema drift parity — none of which may silently redefine `owner_readiness_summary_v1`. |

## 6. Remaining unknowns and follow-up boundary

- External consumers of a stdout-only, never-persisted projection remain
  **unknown** (not provably absent). The manual and schema now state the
  normative key rule for any such consumer.
- The only boundary that would reopen this contract is a **reproduced
  consumer-level failure** (Option B) or a **real persisted-consumer
  requirement** (Option C design goal). Neither exists today.
- **Further Phase 7 engineering is not currently needed.** The controlled
  activation pipeline is implemented and closed through C4-C-R3; the
  remaining open item in the entire Phase 7 chain is the real owner policy
  decision on strict-v2 (ACCEPT/REJECT with provenance), which is a human
  workflow outside any engineering goal and must not be automated or
  synthesized. Until the owner acts, the correct repository state is: stop
  and wait.
