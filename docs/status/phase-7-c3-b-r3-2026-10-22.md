## 3. Implementation (commit `cbf88a4673aa233e852a4879cbb090579871516b`)

`evolution/owner_trust_store.py` (+~25 net lines) and one exported constant in
`evolution/owner_provenance.py`, no persisted contract or schema change:

- `capture_attestation_divergences()` — the R2 shared capture-consistency
  contract consumed by BOTH the strict loader and the audit replay — gains,
  in its record-bearing branch:
  - `RECORD_PROVENANCE_NOT_BOUND_TO_INPUT_BYTES`: the record provenance must
    bind the hash of the **actual** decision-input bytes. The replay's
    duplicated direct check (which compared against
    `bundle.decision_input_content_sha256`) was folded into the shared
    contract under the same stable code name, so replay and strict loading
    now emit the identical named divergence for the identical forgery
    (closing the F1 asymmetry; a simultaneously-rehashed decision-input file
    remains caught by `DECISION_INPUT_BYTES_DIVERGED` plus the recomputed
    dossier comparison).
  - `RECORD_UNSIGNED_SUPERSESSION`: a captured record carrying
    `supersedes_decision_record_id` could not have been produced by the
    capture boundary (`capture_owner_decision_evidence` never sets it and no
    caller passes it); supersession is authorized only through the separately
    signed lifecycle protocol (`AuthenticatedSupersessionBindingV1`, verified
    fresh against `lifecycle_trust_root`), which is unchanged.
  - `AUTHORITY_VERIFIER_KIND_DIVERGED` / `AUTHORITY_ALLOWLIST_DIVERGED` /
    `AUTHORITY_REASON_CODE_DIVERGED`: the record's authority annotations must
    be exactly the deterministic record-time values of the real
    `SignedOwnerProvenanceVerifier` — `verifier_kind ==
    SignedOwnerProvenanceVerifier.kind` (`ed25519-signed-owner-provenance`),
    `allowlist_matched is True`, `reason_code ==
    ED25519_OWNER_PROVENANCE_VERIFIED_REASON`. These annotation fields sit
    outside both the owner signature and the deterministic record id, so only
    the capture boundary could have written them; the free-text `detail`
    stays deliberately unchecked (audit prose, never a security anchor).
- `ED25519_OWNER_PROVENANCE_VERIFIED_REASON` is the new exported constant in
  `evolution/owner_provenance.py` used by both VERIFIED assessment
  constructions (record time and plan time) and by the consistency contract,
  so the pinned value exists exactly once.
- Semantics kept distinct: parseable diverging evidence replays as a named
  `MISMATCH` (CLI exit 1) and strict downstream consumption fail-closes with
  the same machine-readable codes (CLI exit 2 class); honest
  REJECTED/INVALID and INVALID-with-VERIFIED-crypto captures (no record
  embedded) still replay `REPLAYS_BYTE_IDENTICAL`; historical capture
  coherence never grants fresh authority — plan-time re-attestation against
  the operator's CURRENT trust root is untouched, and a genuine signature
  with forged cosmetic annotation text still verifies freshly because plans
  consult only the fresh assessment.

## 5. Limitations and boundaries

- The annotation contract reconciles captured annotation *text* with the
  deterministic record-time values of the one real verifier; it deliberately
  does not pin free-form `detail` prose, does not re-derive the record-time
  C1 economic audit from the bundle (its inputs are not bundle components),
  and historical replay remains explicitly non-authoritative: fresh authority
  is only ever the plan-time re-attestation against the operator's current
  trust root.
- A record whose authority was honestly assessed by a *future* different
  injected verifier implementation would need an explicit capture-contract
  version, exactly like the R2 limitation class for capture variants; every
  legitimate bundle today comes from the always-real-verifier capture
  boundary.
- Directory-level shape and claim checks cannot defend against
  whole-directory replacement by an actor with write permission on the
  evidence root (the standing C2-R2/R1 recorded limitation class);
  deterministic bundle ids and content hashes keep such replacement
  detectable against an independently retained identity. The R2-review's
  deferred locator/basename question is intentionally not addressed (no
  demonstrated requirement; relocated legitimate evidence stays valid).
- Unsigned supersession *outside* evidence bundles (standalone record files
  handed to the resolver/plan) keeps its existing semantics: the resolver
  applies it at face value as unauthenticated bookkeeping and plan-time fresh
  re-attestation rejects it (`OWNER_PROVENANCE_UNSIGNED_SUPERSESSION` →
  `OWNER_AUTHORITY_REVERIFICATION_REJECTED`); this phase changed neither.
