## 2. The defect (parser-confirmed, not prose speculation)

`_next_steps_zh` in `src/turtle_value_engine/evolution/owner_readiness.py`
built two `plan_activation_step` variants that told the operator to reuse
**all** `readiness-summary` inputs for `tve evolution plan-activation`
("传入与上述重放命令完全相同的输入" / "传入与本次 readiness-summary 完全
相同的全部输入"). The real argparse subcommands differ:

| Option | `readiness-summary` (cli.py:993) | `plan-activation` (cli.py:694) |
| --- | --- | --- |
| `--base-profile/--target-profile/--release-manifest/--project-config` | required | required (shared) |
| `--boundary-input/--revocation/--policy-exception/--trust-root/--authority-evidence/--signed-revocation/--signed-supersession` | optional (shared) | optional (shared) |
| `--decision-record` | optional (journey-start view) | **required** |
| `--activation-root` | optional (store classification) | **rejected** (not an option) |
| `--watchlist/--normalized-input/--backtest-manifest/--surface-snapshot/--runner-config` | **rejected** | optional, repeatable (reference inventory) |
| `--output` | **rejected** (no such option) | **required** (writes the plan file) |

Impact: a mechanically copied summary argv containing `--activation-root`
dies at the plan parser with exit 2, and even after dropping the flag the
summary's inputs are not necessarily a complete activation-plan inventory.
No authorization bypass; the operator still chooses `--output` (no
read-only/zero-write breach).

## 9. Follow-up scoping (analysis only — nothing implemented): the
version-aware `summary_id` identity contract

The R1 diagnostic
`test_diagnostic_summary_id_shared_across_distinct_store_problems` pins
that `summary_id` binds the store **status** but not the store
problems/guidance, so two genuinely different observations of one status
share a `summary_id` (distinguished only by `content_sha256`). R3 changed
hint text and thereby every summary's `content_sha256` while `summary_id`
stayed stable — correct under the current semantics, but the semantics
themselves must now be decided deliberately. A future phase must, **before
any code change**:

1. **Decide the identity meaning.** `summary_id` (v1) is a *semantic-core*
   identity over profile/manifest identities+hashes, plan id/content,
   store status, config SHA and journey state — deliberately excluding
   presentation (`next_steps_zh`), store problems/guidance and the config
   path. Options: (i) keep v1 as the *semantic* id and document that
   `content_sha256` is the full-projection discriminator (no code change,
   only contract documentation); (ii) introduce an opt-in v2 whose id
   binds the complete projection (e.g. derived over the canonical payload
   that `content_sha256` covers, or `content_sha256` itself as the v2 id).
   Option (ii) makes hint-text edits change the id — a trade-off that must
   be weighed against replay-comparison use cases that currently benefit
   from a stable semantic id.
2. **v1 compatibility.** `readiness-summary` has no `--output` and writes
   nothing, so no v1 summaries are persisted in any repository store; the
   compatibility surface is the frozen `owner_readiness_summary_v1`
   schema (`schema_version=1.0.0`, unchanged field set), the CLI's stdout
   contract, operator workflows in `owner-readiness-handoff.md`, and the
   R1/R2/R3 test expectations that replay equal `summary_id`. A v2 must be
   additive (new field/contract name or explicit version marker), never a
   redefinition of `summary_id` in place.
3. **Consumers / deduplication key.** Consumers today are humans reading
   stdout and tests asserting replay equality; nothing persists or
   deduplicates by `summary_id`. If a future consumer persists summaries,
   the deduplication key must be decided explicitly — `summary_id` alone
   is insufficient (the collision), `(summary_id, content_sha256)` is
   exact but over-fragile for semantic comparison, so a v2 consumer should
   persist both and key on whichever the chosen contract defines.
4. **No hash cycles.** v1 `content_sha256` is computed over the payload
   before itself is added — any v2 that derives its id from the payload
   must keep the same discipline (id fields excluded from the hashed
   canonical bytes, or id derived last) and must state it in the schema
   description, mirroring the freeze-anchor/binding patterns of Phase 7.
5. **Deliverable shape.** The phase should first produce a written
   contract decision (goal document + schema description updates +
   diagnostic-test fate: the collision test flips to the new expectation
   only together with the contract change), and only then the minimal
   additive implementation with tests-first red evidence — the same
   discipline as R1/R2/R3. R3 implements none of it.
