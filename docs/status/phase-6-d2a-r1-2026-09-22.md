## Delivered corrections

Scope is exactly the four review findings inside
`src/turtle_value_engine/monitoring_runner/lease.py`,
`src/turtle_value_engine/monitoring_runner/service.py` and
`tests/test_monitoring_runner.py`. No schema, contract, CLI surface, Phase
6-A/6-B/6-C/D1 semantics, activation identity, PIT freeze, receipt or systemd
behavior changed.

1. **OS `flock` is the first and only liveness authority.**
   `MonitoringRunnerService.run()` no longer performs any pre-lock
   `validate_record()` read; the removed method no longer exists. `held()`
   tries the non-blocking exclusive lock first, and the persisted record is
   read only after this process owns the kernel lock, so a torn or corrupt
   lease JSON can never preempt a real live-lock classification.
2. **Contention is distinguished from unrelated OS errors.**
   Only the platform's real non-blocking contention errors
   (`BlockingIOError`/`EAGAIN`/`EWOULDBLOCK`/`EACCES`) map to
   `RunnerLeaseBusyError` (CLI `LEASE_BUSY`, exit 3, zero provider/model/
   acquisition/D1 work). Every other open/flock failure — e.g. `ENOLCK`,
   bad descriptor, `EIO` — fails closed as a precise `RunnerLeaseError`.
   `probe()` obeys the same truthfulness rules: an existing slot that cannot
   be opened is never reported `FREE`, and a non-contention lock failure is
   never reported `LIVE`.
3. **Lease records are bound to their slot identity.**
   After acquiring the lock and decoding a prior canonical `RunnerLeaseV1`,
   `held()` requires `record.runner_id == RunnerLease.runner_id`. A
   hash-valid record for runner B found in runner A's slot fails closed with
   an auditable message naming both identities; the foreign record is not
   overwritten and no provider/model/D1 work occurs.
4. **Lease writes prove full-byte persistence.**
   `LeaseHandle.record()` writes through a complete write loop
   (`_write_all_bytes`) that either writes every canonical byte and fsyncs,
   or raises a typed `RunnerLeaseError` on short-write/zero-progress/OS
   failure. A partial JSON payload can never be treated as a successful
   holder-record update. No second lease/state mechanism was introduced.

## Automatic verification

`tests/test_monitoring_runner.py` grew from 25 to 34 deterministic cases.
The nine new R1 regressions prove, without timing or sleep-based races:

- a real held `flock` plus a torn/unreadable lease record classifies the
  second runner `RunnerLeaseBusyError` with zero D1/provider calls, both at
  the service boundary and through the CLI exit-code-3 `LEASE_BUSY` path;
- after that live holder releases, the same corrupt abandoned record fails
  closed as `RunnerLeaseError` (probe reports `ABANDONED`/`corrupt: true`)
  before any activation or D1 work;
- an injected `ENOLCK` flock failure yields `RunnerLeaseError`, never
  `RunnerLeaseBusyError`, with zero D1/provider work, and `probe()` fails
  closed instead of reporting `LIVE`;
- an injected `EIO` open failure on an existing slot yields `RunnerLeaseError`
  from both `probe()` and `run()` instead of reporting `FREE`;
- a canonical `RunnerLeaseV1(runner_id="runner-b")` written into runner A's
  slot fails closed, is not overwritten, and performs zero work;
- per-call 7-byte/5-byte fragmented `os.write` still publishes a complete
  byte-identical canonical record (handle-level and full-service-level);
- zero-progress and mid-write `EIO` injections raise explicit typed
  failures and never publish a truncated record as success.
