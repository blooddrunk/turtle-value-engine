## 6. 下一执行目标：M2-C Futu OpenD

M2-C 分为两个连续但不同性质的 gate：

```text
M2-C1  adapter / provenance / compiler integration + offline fake-client tests
M2-C2  owner-runtime recent + older live probe and bounded acquire/replay evidence
```

M2-C1 可以由 Codex 在没有 owner OpenD 的环境中完成。它应复用现有 acquisition/CAS
architecture，用 injected fake client 保证普通 CI 完全离线，并把 Futu Python SDK 视为
optional provider dependency；不要让 ordinary deterministic analysis 因 Futu SDK 缺失而
无法 import。SDK export 必须明确标记为 provider SDK representation（例如
`futu-opend-sdk-export-v1`），不能称为 raw OpenD wire bytes。

M2-C2 才决定 source selection。必须使用 owner OpenD runtime 实际接受/返回的 H listing
identity，执行近期和至少早一年以上两个不重叠窗口，强制 daily + unadjusted；成功后再做
bounded acquire -> private CAS/envelope -> compile -> `--verify-replay`。

M2-C 必须保留三种不同结果：

1. **FUTU_SELECTED**：M2-C1 完成，owner live 双窗口成功，bounded acquire/replay 稳定；
   Futu 获得 bounded H `MARKET_BAR` role，随后进入 M2-E selection record，不实现 M2-D。
2. **FUTU_EVIDENCE_SUPPORTED_FAILURE**：M2-C1 完成，并且 owner 的真实 OpenD runtime
   实际完成 probe 后得到 quota/entitlement/history/schema/coverage 等证据支持的失败，或
   provider representation 无法在不破坏 acquisition audit boundary 的前提下实现；记录精确
   blocker，然后 M2-D 成为下一候选。
3. **BLOCKED_ON_OWNER_LIVE_PROBE**：Codex runner 无法访问 owner 的 OpenD、OpenD 尚未
   安装/登录/配置，或没有 owner-runtime live evidence。此时可以关闭 M2-C1 代码边界，但
   **不得**把执行环境限制解释成 Futu provider failure，也不得提前进入 M2-D；应输出 owner
   可直接执行的 private live-probe 命令并保持 M2-C2 pending。

当前 Futu 官方接口文档仍提供 historical candlestick、分页 key、历史 K 线 quota 查询和
复权类型参数；实现时应以运行时 SDK/API contract 为准，并显式设置 unadjusted，而不是依赖
接口默认的复权模式。
