## 3. Implementation (commit `814779019846278ea5490d61298b8cd8c7a17bc9`)

`evolution/owner_trust_store.py` (+~120 lines), no persisted contract or
schema change:

- `capture_attestation_divergences()` — **one** shared capture-attestation
  consistency contract used by both the strict loader and the audit
  replay: `VALID` ⇔ empty `validation_blockers` (symmetrically
  `INVALID_STATE_WITHOUT_BLOCKERS`); a record-bearing bundle is a signed
  capture, so its record authority must be exactly
  `OWNER_AUTHORITY_VERIFIED` through an `INJECTED_VERIFIER` **and** the
  recomputed dossier must be `VERIFIED` (`AUTHORITY_STATUS_INCONSISTENT`,
  `AUTHORITY_METHOD_INCONSISTENT`) — an honestly rejected signature can
  never establish historic VERIFIED authority, and a REJECTED/UNVERIFIED
  authority could never have produced a record inside a VALID bundle; the
  attested key id equals the dossier `key_id`
  (`ATTESTED_KEY_DIVERGED`), the attested registry id/content hash equals
  the registry inside the persisted snapshot
  (`ATTESTED_REGISTRY_DIVERGED`), and the authority
  `evidence_content_sha256` equals the hash of the actual decision-input
  bytes (`EVIDENCE_HASH_DIVERGED`).
- `reverify_owner_decision_evidence` appends those named codes as
  mismatches (CLI exit 1, machine-readable); `load_owner_decision_evidence`
  (the `plan-activation --authority-evidence` consumer) now additionally
  recomputes the dossier from the actual persisted bytes, requires equality
  with the captured one, and fail-closes on every attestation divergence
  (CLI exit 2 class).
- Semantics kept distinct: historical replay integrity and capture
  coherence never grant fresh authority (plan-time re-attestation against
  the operator's CURRENT trust root is untouched); the record-time economic
  audit is deliberately not re-executed from the bundle (its inputs are not
  bundle components); legitimately captured evidence is preserved — honest
  REJECTED/INVALID and honest INVALID-with-VERIFIED-crypto bundles still
  replay `REPLAYS_BYTE_IDENTICAL`.

`docs/operations/owner-provenance-walkthrough.md` §0/§1/§5 and the failure
table: private directory created `mkdir -m 700` and forced to 0700; the
encrypted PKCS#8 Ed25519 key written through one exclusive
`O_WRONLY|O_CREAT|O_EXCL|O_NOFOLLOW` open at mode **0600 from the first
byte** (umask-independent; existing file or symlink destination refused
atomically with a clear write-once message; `fsync` before close);
passphrase still prompted interactively (`getpass`, never argv/Git/CI/chat);
documented `ls -l` 0600 check, updated exit-1 divergence names and failure
table rows.

The F2 tests execute the exact documented §1 heredoc (extracted verbatim

## 5. Limitations and boundaries

- The attestation contract reconciles captured *claims* with
  cryptographically recomputable *facts*; it does not re-derive the
  record-time C1 economic audit from the bundle (those inputs are not
  bundle components), and historical replay remains explicitly
  non-authoritative: fresh authority is only ever the plan-time
  re-attestation against the operator's current trust root.
- Directory-level shape and claim checks cannot defend against
  whole-directory replacement by an actor with write permission on the
  evidence root (the C2-R2/R1 recorded limitation class); deterministic
  bundle ids and content hashes keep such replacement detectable against
  an independently retained identity.
- The strict `record.authority == OWNER_AUTHORITY_VERIFIED` rule for
  record-bearing bundles is exact capture semantics: every legitimate
  bundle record comes from the always-verifier-injected capture boundary
  (an honest REJECTED capture stores no record). A hypothetical future
  capture variant that persisted UNVERIFIED records inside bundles would
  need an explicit contract version, not a silent pass.
- The walkthrough tests prove the documented procedure with throwaway
  keys/passphrases only; real owner key custody, strict-v2 economic
  acceptance and any activation remain explicit human decisions.
