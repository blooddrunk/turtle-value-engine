## Implemented boundary

- Candidate and record finals use opened canonical directory descriptors, fsynced temporary files and no-overwrite hardlink publication. Directory fsync follows each new final. A concurrent identical file is reused; a concurrent different file is preserved and conflicts.
- Candidate publication precedes the materialization record. A normal second-stage failure removes the candidate only if this invocation still owns its inode and no record has appeared. Pre-existing candidates and concurrent replacements are preserved.
- `resolve_complete_materialization_pair` requires both final artifacts as regular non-symlink files, validates the `CandidateProfileMaterializationV1` record and candidate `RuleProfile`, checks the candidate id and compares the hash of the exact candidate bytes with `candidate_content_sha256`. The CLI invokes it before exit 0.
- The active rule root is derived from the actual `--base-profile` parent. Supplied inputs and the authoritative workspace remain forbidden. The CLI publishes through the same canonical destinations it validated, with a directory-descriptor check against redirection.
- A process death may leave an orphan candidate; it is not a committed materialization without a final valid record, and the resolver rejects it. No cross-filesystem atomic-pair claim is made.
