The review then audited the auditability of the C3-A chain itself. A
standalone six-check adversarial reproduction (one throwaway Ed25519 key;
two valid registries with the same key set — therefore the same derived
`registry_id` — but different trust content that both verify the same
signed statement; the real `validate_owner_decision` record-time capture
and `plan_profile_activation` re-attestation flows) was executed on the
pristine baseline. **All six checks showed the defect:**

| Check | Baseline `ce9726d` | Hardened `04bc196` |
|---|---|---|
| same key set under different trust content shares one `registry_id` | DEFECT | shows by design (root cause; the content hash is the content identity) |
| different trust roots share one `verification_id` (identity collision) | **DEFECT** | OK — identities diverge |
| dossier value set carries no registry content snapshot | **DEFECT** | OK — exact hash recorded |
| persisted VERIFIED record has no structured trust-root identity | **DEFECT** | OK — `attested_*` fields captured |
| two different trust roots reach byte-identical READY plans | **DEFECT** | OK — plans diverge |
| READY plan names no attesting registry anywhere | **DEFECT** | OK — registry id + content hash bound |

Why this is a defect class: `docs/architecture/owner-provenance-verification.md`
§4 explicitly promised "registry id and content hash are bound into every
verification dossier" while the implementation bound only the
content-insensitive `registry_id`; the VERIFIED record named its key only in
prose (violating AGENTS §6 first-class evidence identity); and the
owner-facing READY plan could not state which trust root re-attested its
authority. No privilege escalation existed (forged VERIFIED claims still
cannot reach READY) — the class is audit integrity of the one input whose
content decides trust. C3-B evidence capture cannot be built on artifacts
that cannot name their trust root.

## 2. Hardening implemented (tests-first `bea7f56`, fix `04bc196`)

1. **Dossier binds the registry content** (`evolution/owner_provenance.py`):
   `OwnerProvenanceVerificationV1.registry_content_sha256` is required and
   participates in the `verification_id` derivation, so one verification
   identity names one exact trust-root content. The canonical nine-check
   sequence, its per-position schema pin and every check semantic are
   unchanged.
2. **Assessment captures structured attested identity**
   (`evolution/owner_decision.py` + verifier): `OwnerAuthorityAssessmentV1`
   gains additive optional `attested_key_id`, `attested_registry_id`,
   `attested_registry_content_sha256`, populated by
   `SignedOwnerProvenanceVerifier` on every assessment (VERIFIED and
   rejected — honest bookkeeping even on failure). They are captured
   evidence metadata, never authority: a forged record claiming foreign
   attested fields is inert, because plan-time authority always comes from
   the fresh injected-verifier assessment (pinned by regression).
3. **Plan binds the fresh re-attestation trust root**
   (`evolution/activation_plan.py`): `ProfileActivationPlanV1` gains
   `authority_reverification_registry_id` /
   `authority_reverification_registry_content_sha256`, sourced exclusively
   from the fresh re-attestation assessment inside
   `_reverify_decision_authority` (never the persisted record claim),
   required to be supplied together or not at all, and included in the
   `plan_id` derivation — two different trust roots can never produce the
   same READY plan identity.
4. **Deliberate non-goal preserved**: a verifier that attests no trust root
   (the generic C2 fake fixtures, any future non-registry trust model)
   follows the unchanged C2/C2-R1 rules; the fields stay visibly `None`
   and no new READY-blocking rule is imposed on the verifier interface.
   No CLI surface changed; no signed supersession/revocation protocol was
   invented (still C3-B); no activation executor exists.
5. **Schemas**: five regenerated from the models
   (`owner-provenance-verification`, `owner-policy-decision-record`,
   `owner-policy-decision-revocation`, `owner-policy-decision-validation`
   — the record-embedding schemas inherit the additive assessment fields —
   and `profile-activation-plan`); drift-parity tests enforce them.
   Architecture doc gains §3.2 and the §4/§5 wording now matches the
   implementation.

## 5. Residual risks and next package

- `registry_id` remains key-set-derived by design (the content hash is the
  content identity); every downstream identity now binds the content hash,
  and the root-cause property is pinned by regression so a future change
  cannot silently rely on the id as a content identity.
- Attested fields on a record are untrusted bookkeeping by construction;
  the plan binds only the fresh verifier's attestation (pinned). A future
  package may cross-check record-time vs plan-time trust-root drift as an
  owner-visible warning, but drift is legitimate (key/registry rotation)
  and must not block.
- C3-B remains the next separately selected package: trusted registry
  lifecycle/persistence, evidence capture of dossiers, the versioned signed
  revocation/supersession protocols, and record/CLI integration. R2 gave
  those artifacts the content-addressed trust-root binding they require.
