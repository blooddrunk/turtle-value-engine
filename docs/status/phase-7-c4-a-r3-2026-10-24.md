### F2 — externally hard-linked final lock inode (4 red)

`activation_root/locks/` is a legitimate real directory; the hostile entry
is only the final component `locks/<sha256-of-config>[:24].lock`, planted
with `os.link` on the same temporary filesystem (link count 2, identical
`st_ino`/`st_dev` with the outside-store trap, asserted before driving the
CLI; the trap lives under `tmp_path/outside-store/`):

| hostile layout | observed pristine-main behavior |
| --- | --- |
| pre-planted `os.link(trap, lock)` (apply, no external flock) | CLI **exit 0 `ACTIVATED`** — `O_NOFOLLOW` passed (not a symlink), `fstat(S_ISREG)` passed (it is a regular file), and `flock` bound the executor's mutual exclusion to the inode also reachable outside the store; trap bytes unchanged (the lock is never written) |
| same layout, trap flock held by the test process | CLI **exit 3 `ACTIVATION_BUSY`** — a foreign-inode flock fabricated genuine-busy semantics (exit 3 must mean only real contention on the in-store lock) |
| attacker `os.link(lock, trap)` after a real apply (rollback) | CLI exit 0 `ROLLED_BACK` through the now-externally-shared lock inode |
| same post-apply layout, trap held (rollback) | CLI exit 3 `ACTIVATION_BUSY` |

Controls that stayed green on pristine main: the executor-created lock
entry and the reused entry of a later rollback both have `st_nlink == 1`
and work normally; the R2 suite keeps pinning the pre-existing regular
lock file, the directory lock target and the real two-process 0/3
contention pair. The hardlink probes skip (with an explicit filesystem
report) on any filesystem that refuses `os.link`; Linux CI hosts run them.

## 3. Minimal fixes (both reproduced; smallest compatible repairs)

`src/turtle_value_engine/cli.py` (F1):

- `_prepare_activation_inputs` now records, under
  `prepared_input_file_sha256s`, the SHA-256 of every **actually
  supplied** preloaded named input file — `decision-record[i]`,
  `revocation[i]`, `policy-exception[i]`, `signed-revocation[i]`,
  `signed-supersession[i]` and `boundary-input` — i.e. exactly the files
  whose contents become prepared in-memory objects before the config
  lock. Profiles, manifests and the project config are re-read fresh
  inside the executor and are deliberately not reread or reclassified
  here; the trust root and evidence bundle keep their own identity
  recheck.
- `_build_activation_authority_recheck` (still injected only into the
  apply path) extends the same closure that the R2 anchors already run:
  at both anchor points every prepared input file must still be readable
  and byte-identical, otherwise the named blockers
  `AUTHORITY_INPUT_UNREADABLE:<label>` / `AUTHORITY_INPUT_CHANGED:<label>`
  fail the apply closed as `ACTIVATION_AUTHORITY_STALE` (exit 1) before
  the protected mutation. The recheck is also built when no trust root is
  supplied but named input files exist; the trust-root reload branch
  itself runs only when a trust root was actually supplied. The read-only
  preview and the planner command are unchanged; library callers keep the
  explicit in-memory verifier contract (`None` performs no recheck).

`src/turtle_value_engine/evolution/activation_execution.py` (F2):

- `_ConfigLock.__enter__` additionally rejects the opened lock descriptor
  when `fstat` reports `st_nlink != 1` (named status
  `ACTIVATION_LOCK_HARDLINK`, exit 2) — after the symlink/regular-file
  checks, before any `flock`. The lock must be an inode with exactly one
  directory link, the in-store one; the hostile entry and its foreign
  twin are never unlinked or altered (no "delete stale lock" recovery
  exists). `ACTIVATION_BUSY` keeps meaning only genuine flock contention
  on the in-store single-link lock, so a held external hardlink is the
  multi-link refusal, never exit 3. Ordinary creation (`O_CREAT`,
  `st_nlink == 1`) and single-link reuse are unaffected; rollback
  benefits from the same hardened lock entry.

No persisted contract field or schema changed; `FAULT_POINTS`, receipts,
rollback intents/outcomes, fsync ordering, guards and every C4-A/R1/R2
status are unchanged. The R2 TOCTOU honesty boundary carries over
unchanged: the anchors observe the on-disk state at two points inside the
lock; a change landing in the remaining microseconds before the
same-directory `os.replace` is outside what this single-host executor can
prevent without cross-file global atomicity, which is not claimed.

## 7. Not verified / explicit residual boundaries

- No physical power-loss or multi-host concurrency certification (as in
  R1/R2): interruption evidence is deterministic fault/monkeypatch
  injection plus fsync-call ordering proofs inherited unchanged.
- The R3 anchors observe the prepared inputs at the same two anchor points
  as R2; the residual window between the last anchor and the
  same-directory `os.replace` remains honestly unguarded (no cross-file
  global atomicity is claimed or implementable here).
- The `st_nlink != 1` containment observes the link count at lock
  acquisition; an attacker linking a second name to the lock inode after
  that observation (while the executor holds the flock) does not weaken
  the executor's mutual exclusion — the flock stays bound to the in-store
  inode — but the inode becomes externally observable until the next
  invocation, which then refuses it.
- A cosmetic byte change to a supplied input file mid-invocation is
  conservatively refused (`AUTHORITY_INPUT_CHANGED`), exactly like R2's
  conservative `AUTHORITY_TRUST_ROOT_SUPERSEDED` on any snapshot
  supersession; the operator reruns preview + apply. This is intended
  fail-closed semantics, not a false-positive class.
- The boundary-input and signed-lifecycle file classes were not probed
  adversarially (the goal prioritized the hash-bound policy exception,
  then the decision record); they are covered by the same generic
  prepared-input identity comparison, and their fresh-invocation blocking
  semantics are pinned by the C2/C3-B suites.
- No R4 exists or is implied; any further hardening needs new
  independently reproduced evidence.
